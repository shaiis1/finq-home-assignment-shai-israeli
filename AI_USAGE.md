# AI Usage

This entire project was built with **Claude Code** (Anthropic's CLI agent, Claude Sonnet 5),
used deliberately and heavily — not just for autocomplete-style suggestions. Full disclosure of
how, since the assignment explicitly permits AI use "as long as every line is defensible."

## Workflow

1. **Spec intake** — Claude read the assignment PDF directly and summarized the requirements
   before any code was written, to confirm shared understanding with me before starting.
2. **Planning** — I asked for a concrete step-by-step plan (repo setup → design docs → build →
   QA → deliverables) before implementation began, and reviewed it before agreeing to proceed.
3. **Multi-agent build, checkpointed after every phase** — I explicitly asked Claude to run this
   as an "agent team": separate, context-isolated subagents playing PM, Architect, Developer, and
   QA roles, with **my review and sign-off required after each phase** before moving to the next
   (not a single autonomous pipeline). Concretely:
   - A **PM agent** wrote `docs/planning/pm-breakdown.md` — task breakdown and the exact
     acceptance criteria for the save/update/delete state machine (Flows A–D).
   - An **Architect agent**, given the PM's breakdown, wrote `docs/planning/architecture.md` —
     file structure, the Pinia store design (shared collection, derived getters), and the full
     API contract.
   - **Developer agents** (backend, then frontend) implemented against the architecture doc.
   - **QA agents** — first one comprehensive agent, then split into two narrower parallel agents
     (backend code review + curl edge cases; live browser testing of the remaining flows) after
     the first hit a context limit — exercised the app and reported findings.
4. **Human review at every stage, not just at the end** — I read every design doc and every
   generated file (store, views, routes, validation, repository) before accepting it, ran
   `npm run typecheck` / `tsc --noEmit` after each implementation phase, and independently
   smoke-tested the backend with my own `curl` calls rather than trusting the developer agent's
   self-report.
5. **A bug the agents missed, found by manual testing** — the frontend developer agent disclosed
   it had no browser access and could only reason about the code statically. Live-testing the app
   myself in Chrome (via Claude's browser-automation tools) surfaced a real bug it had missed:
   `RandomListView.vue` re-fetched a brand-new random batch on every mount, which silently wiped
   out a just-saved profile on Back-navigation. I diagnosed and fixed this directly rather than
   re-delegating it.
6. **QA findings triaged, not auto-applied** — the QA agents reported one Major finding (no
   in-flight guard on Save/Update/Delete, allowing a fast Save→Update sequence to race) plus
   several minor items. I read the actual code the finding referenced to confirm it was real
   before fixing it, asked the user which findings were worth fixing given the time box, then
   implemented and re-verified the fix live in the browser myself.
7. **Deliverable docs** (this file, `README.md`, `DECISIONS.md`) were drafted by Claude and
   reviewed/edited by me.

## What Claude generated vs. what was manually reviewed/changed

- **Generated by AI, reviewed by me before acceptance:** essentially all application code —
  Pinia store, views, components, router, API clients, Express routes, SQLite repository,
  validation. Every file was read (several in full) before being committed.
- **Manually written/fixed by me directly:** the `RandomListView.vue` re-fetch bug fix, and the
  in-flight-action-guard fix (`pendingActionId`) plus its UI wiring, after independently verifying
  the QA finding against the actual code rather than accepting the report at face value.
- **Verification was never delegated to "trust the agent's word":** typecheck runs, backend curl
  tests, and live browser walkthroughs (including deliberately killing the backend mid-action to
  confirm the optimistic-rollback extension actually rolls back) were all run and observed
  directly, not just reported by a subagent.

## Why this workflow, briefly

The goal was to use AI the way a senior engineer would use a capable but junior team: delegate
well-scoped work with a clear spec, but review every output, verify claims independently, and take
direct responsibility for bugs — rather than accepting AI output uncritically. The multi-agent
structure with mandatory checkpoints (PM → Architect → Developer → QA, each reviewed before the
next started) was a deliberate choice to keep a human decision point at every architectural fork,
consistent with the assignment's stated evaluation priority: judgment and decisions first, code
quality second.
